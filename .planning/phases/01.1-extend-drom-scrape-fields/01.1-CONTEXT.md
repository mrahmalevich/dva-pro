<decisions>
## Implementation Decisions

### Resume granularity (cursor)

- **D-01:** Cursor extends to per-trim resolution. Add `lastComplectationIndex: number | null` to `cursor.json` next to existing `lastBrandSlug` / `lastModelSlug`. On resume mid-generation, the per-comp loop skips already-fetched trims using the saved index. Worst-case refetch on a fresh resume is the trim that was in flight when the run died (≤ 1 page).
- **D-02:** Cursor write cadence is **every trim** (no throttling). The BMW pilot's ~2 000 trim writes are cheap (`writeFileSync` on a sub-1KB JSON), and the simpler invariant is worth the trivial I/O.
- **D-03:** Crossing into a new generation resets `lastComplectationIndex` to 0 (or `null`); the existing `CursorSchema` (Phase 01-11) extension must remain backward-compatible — a cursor written by Phase 01 (without the index) loads as `lastComplectationIndex = null` and the per-comp loop starts from 0.
- **D-04 (open for planner):** Whether `lastGenerationSlug` also needs to enter the cursor schema (today the cursor stops at brand+model — but the per-comp loop iterates trims of multiple generations within one model). Planner decides during plan-phase based on a closer read of `drom/index.ts`.

### Coverage metric formula (`report.json.field_coverage[group]`)

- **D-05:** Per-trim, majority-threshold formula. For each trim, a group is "covered" if **≥ ⌈2/3 × leaf_count⌉** of its leaves are non-null. The group's coverage is `count(covered trims) / total_trims`. Gate: each of the six groups ≥ 0.70 across the BMW pilot.
- **D-06:** Threshold table (precomputed; planner / verifier hardcodes from this list — no runtime ceil math):
  - Identity (7 leaves)   → ≥ 5 non-null per trim
  - Pricing (2 leaves)    → ≥ 2 non-null per trim (effectively all)
  - Drivetrain (6 leaves) → ≥ 4 non-null per trim
  - Dimensions (9 leaves) → ≥ 6 non-null per trim
  - Comfort (6 leaves)    → ≥ 4 non-null per trim
  - Tires (2 leaves)      → ≥ 2 non-null per trim (effectively all)
- **D-07:** Pricing and Tires both collapse to "all leaves required" because ⌈2/3 × 2⌉ = 2. This is intentional — for these two-leaf groups, partial extraction is not informative. If tire extraction in practice falls below 70% of trims, the planner should surface this as a SPEC.md adjustment request rather than silently weakening the formula.
- **D-08:** `field_coverage` lives in `report.json` as a top-level object next to existing `image_failure_rate`. Snapshot golden (`bmw-pilot.test.ts.snap` per SPEC R-8) locks the six rates rounded to 2 decimal places.

## Field Findings (post-execution, 2026-04-29)

Recorded after Wave 5 paused at the BMW pilot manual gate (Plan 01.1-09 Task 4). One real-world defect surfaced during the live BMW sweep that blocks the SPEC R-7 verification. This addendum scopes the fix as a gap-closure plan to be created by `/gsd-plan-phase 01.1 --gaps`.

### F-01: HTTP 431 cookie-jar bloat in `shared/http.ts` (BLOCKING)

**What happened:** `DROM_BRAND_WHITELIST=bmw pnpm scrape:drom` ran successfully for ~1h28m walking BMW models, then failed with `HTTP 431 Request Header Fields Too Large` on `GET https://www.drom.ru/catalog/bmw/1-series/g_2007_23507/`.

**Root cause:** Drom sets a feedback-widget cookie named `npsPayload` whose value is a base64-encoded list of component IDs. Drom appends a comp ID every time the client visits a `/catalog/*` page. Across a long crawl, the cookie value grows unboundedly — by the time of the 431, `npsPayload.value` was ~8 KB (verified in the failed-request cookie dump). The full outgoing `Cookie:` header — `npsPayload` plus ~10 other drom cookies (`ring`, `segSession`, `PHPSESSID`, `cookie_cityid`, `cookie_regionid`, `my_geo`, `dr_df`, `veryFirstHit`, `npsType`, `showNPS`) — exceeded drom's nginx `large_client_header_buffers`, so requests fail before reaching the app server. This is **not** bot detection — a fresh `curl` with no cookies returns 200 on the same URL.

**Why Phase 01 / Phase 01.1 unit tests didn't catch it:** Phase 01's runs were shorter and on shallower brand depths, so `npsPayload` never crossed the threshold. Phase 01.1's automated tests are all fixture-driven (no live HTTP), so this is unreachable from the test suite as it stands.

**Mechanic location:** `server/scrapers/shared/http.ts:20` instantiates a single module-scope `tough-cookie` `CookieJar` and passes it to `got.extend({ cookieJar })` at line 47. Every `Set-Cookie` is stored, every subsequent request replays the entire jar.

### Decisions (locked for the gap-closure plan)

- **D-09:** Fix is a denylist of NPS / feature-flag cookies, not a wholesale jar wipe or a session-cookie allowlist. Strip exactly `npsPayload`, `npsType`, `showNPS` from the outgoing `Cookie` header on every drom request. The cookies that drom genuinely needs server-side (load-balancer affinity: `ring`, `segSession`, `PHPSESSID`; region: `cookie_cityid`, `cookie_regionid`, `my_geo`; bot-fingerprint hints: `dr_df`, `veryFirstHit`) keep flowing untouched.
- **D-10:** Implementation goes in `server/scrapers/shared/http.ts` as a `got.extend({ hooks: { beforeRequest: [...] } })` hook on the existing `dromClient`. Filter at the outgoing-header layer — leave the cookie jar itself untouched so any internal `tough-cookie` round-trip behaviour stays intact.
- **D-11:** Cookie-strip set lives as a module-scope `STRIP_COOKIES = new Set([...])` constant in `http.ts`, sized to grow if drom adds new bloat cookies. This is preferable to an env var (operational simplicity) or a config file (overkill for three names).
- **D-12:** Regression test goes in `server/tests/http.test.ts` (existing file; already covers `pLimit(1)` serial-fetch). Test pattern: stub a got-compatible request, assert the outgoing `Cookie:` header strips `npsPayload`/`npsType`/`showNPS` and preserves the others. No live network, no fixture HTML.
- **D-13:** No SPEC.md change. The R-5 / R-7 / R-8 acceptance criteria stand — this is a defect in the existing rate-limiter / HTTP module, not a new requirement.

### Out of scope for the gap-closure plan

- **No allowlist mode.** A future phase can flip to allowlist if drom adds more bloat cookies; for now, denylist of three known names is the smallest reasonable change.
- **No CookieJar replacement.** `tough-cookie` continues as the storage layer — only the outgoing-header projection changes.
- **No retry-on-431 logic.** If drom adds new bloat cookies after this fix, the 431 will fire again and we'll iterate. Adding generic 431-retry would mask future regressions.

### Verification path after the fix

1. `pnpm test http.test.ts` — new strip assertion green, existing serial-fetch + retry tests still green.
2. `DROM_BRAND_WHITELIST=bmw pnpm scrape:drom` — run end-to-end without 431; `report.json.field_coverage` populates with all six rates ≥ 0.70.
3. Plan 01.1-09 Task 4 (BMW pilot manual gate) closes against this run, finalising the phase.
