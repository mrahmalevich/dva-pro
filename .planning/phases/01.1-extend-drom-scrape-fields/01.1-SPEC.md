# Phase 01.1: extend-drom-scrape-fields — Specification

**Created:** 2026-04-29
**Ambiguity score:** 0.13 (gate: ≤ 0.20)
**Requirements:** 8 locked

## Goal

Extend the drom catalog scraper to walk per-complectation detail pages and persist a full per-trim record (identity, pricing, drivetrain, dimensions, comfort, tires) nested inside each `ModelRecord`, validated end-to-end against a BMW-only pilot sweep.

## Background

Phase 01 delivered a working drom catalog scraper that fetches generation pages and extracts one `ModelRecord` per generation. Today's record holds engine/drive/price aggregates rolled up across all complectations of a generation:

- `parse-generation-page.ts` reads `meta[name=description]`, the `<h1>` body-types, all `<div class="r6hmq22">` engine-spec lines, and the `<td class="y7l57t0">` price cells, producing `engine_options[]`, `drive_options[]`, `price_min_rub`, `price_max_rub`.
- The complectation table on every generation page contains 1–35 individual trim rows. Each row already carries: trim name (`xDrive 25d AT Business`), production period (`04.2020 - 03.2022`), price (`7 190 000 ₽`), tier label (`Базовая`/`Предмаксимальная`/`Максимальная`), engine code (`B47B20`), frame code (`G05`), and a link to a per-complectation detail page (`/catalog/bmw/x5/<comp_id>/`).
- We do not currently fetch those per-complectation detail pages. Dimensions (length/width/height/wheelbase/clearance/trunk), curb/gross weight, fuel consumption, tank volume, seats, doors, transmission gear count, and tire spec strings live there.
- The current rate limiter (`server/scrapers/shared/http.ts`) holds a fixed 10–15 s delay (`pLimit(1)` + sleep). For a BMW-only pilot (~2 000 per-comp pages) this is workable; for a full 50-brand sweep it would take ≈ 3 weeks continuous. The user has chosen the BMW pilot, deferring multi-brand expansion to v1.x.
- The existing `ModelRecord` zod schema in `server/scrapers/shared/types.ts` has no `complectations` field. This phase adds it as a nested array; `models.json` record count stays the same, but each record grows.

## Requirements

1. **Per-complectation parser**: A new module parses one drom complectation detail page into a `Complectation` sub-record.
   - Current: No per-complectation parser exists. The orchestrator never fetches `/catalog/<brand>/<model>/<comp_id>/`.
   - Target: `server/scrapers/drom/parse-complectation-page.ts` exports `parseComplectationPage(html, ctx) → Complectation`. Every field is best-effort — failure to extract any field emits the record with that field as `null`, never throws.
   - Acceptance: Unit tests against ≥ 3 captured BMW complectation fixtures verify field extraction; missing-section fixtures verify null-emission (not throw).

2. **Complectation schema (nested)**: `ModelRecord` gains a `complectations[]` field; new zod sub-schema defines the per-trim shape.
   - Current: `ModelRecord` ends after `image_paths`; no per-trim shape.
   - Target: `ModelRecord.complectations: Complectation[]` where `Complectation` is `{ identity, pricing, drivetrain, dimensions, comfort, tires }` with every leaf field nullable.
   - Acceptance: `pnpm typecheck:server` exits 0; `models.json` written by the BMW pilot contains a non-empty `complectations` array on every `ModelRecord` whose generation page lists ≥ 1 trim row.

3. **Field groups (six locked groups, every leaf nullable)**: The `Complectation` schema partitions trim data into six groups, each populated independently.
   - Current: None of these field groups exist on disk.
   - Target:
     - **Identity** — `name`, `period_from`, `period_to`, `tier`, `engine_code`, `frame_code`, `source_url`. From catalog generation page (already-loaded HTML, 0 extra HTTP).
     - **Pricing** — `price_new_rub`, `price_used_from_rub`. From catalog generation page (used price is sparse — null when not present).
     - **Drivetrain** — `engine_cc`, `engine_hp`, `engine_fuel`, `drive`, `transmission_type` (`AT`/`MT`/`CVT`/`AMT`), `transmission_gears`. cc/hp/fuel/drive from generation page; transmission_type derivable from trim name; transmission_gears from per-comp page.
     - **Dimensions** — `length_mm`, `width_mm`, `height_mm`, `wheelbase_mm`, `clearance_mm`, `trunk_min_l`, `trunk_max_l`, `curb_weight_kg`, `gross_weight_kg`. All from per-comp page.
     - **Comfort** — `seats`, `doors`, `fuel_consumption_city_l`, `fuel_consumption_highway_l`, `fuel_consumption_combined_l`, `tank_l`. All from per-comp page.
     - **Tires** — `tires_front`, `tires_rear` (raw spec strings). All from per-comp page.
   - Acceptance: Zod schema accepts a record where every group's fields are `null`; rejects a record missing a group entirely (group key must be present).

4. **Orchestrator integration (BMW pilot)**: The drom orchestrator fetches per-complectation pages for every BMW trim row found on every BMW generation page.
   - Current: Orchestrator visits brand → model → generation pages only. No per-comp fetches.
   - Target: After parsing each generation page, the orchestrator iterates the trim rows it surfaced, fetches each `<comp_id>` detail URL through `shared/http.ts`, and parses it via `parseComplectationPage`. The brand filter for this phase is hard-coded to `["bmw"]`. Other brands skip the per-comp loop entirely.
   - Acceptance: A BMW-only pilot run fetches ≥ 1 per-comp page per BMW generation; no per-comp fetch attempted for any non-BMW brand (verified via `report.json.pages_visited` brand breakdown or fetch log).

5. **Probe-down rate limiter**: `shared/http.ts` adopts a probe-down algorithm replacing the fixed 10–15 s delay.
   - Current: Fixed delay (10–15 s) per request; no adaptation.
   - Target: Start delay = 10 s. After 100 consecutive 200 OK responses, halve the delay (10 → 5 s, floor 5 s). On any 429 / 5xx / block-detection match, reset delay to 10 s for the next 100 requests. Invariant: delay never drops below 5 s, never exceeds 10 s.
   - Acceptance: Unit test simulates 100 OK responses → asserts delay halves; injects a 429 → asserts delay resets to 10 s; floor never crossed.

6. **No-must-have tolerance**: Failure to extract any field group does not abort the trim record or the run.
   - Current: Existing `parse-generation-page.ts` throws on zod failure (Pitfall 1 mitigation).
   - Target: `parseComplectationPage` catches its own zod-validation and field-extraction errors; returns a record with the failed group's leaves as `null` plus a `_extraction_errors[]` annotation. The orchestrator persists the record and pushes a `kind: 'parse'` entry into `report.errors[]` for observability — but does not abort.
   - Acceptance: A captured fixture with a deliberately broken dimensions table emits a complectation record where the entire `dimensions` group is `null`; the run completes with `final_status: 'ok'`.

7. **Per-field-group coverage threshold (BMW pilot)**: Each of the six field groups must reach ≥ 70 % non-null leaf coverage across all BMW complectations.
   - Current: 0 % — none of these fields are extracted today.
   - Target: After the BMW pilot run, `report.json` includes a `field_coverage` object: `{ identity: 0.92, pricing: 0.85, drivetrain: 0.78, dimensions: 0.74, comfort: 0.81, tires: 0.71 }`. Run is rejected if any group < 0.70.
   - Acceptance: `report.json.field_coverage[group] ≥ 0.70` for all six groups on the BMW pilot run.

8. **Snapshot golden + HTML viewer screenshot**: BMW pilot output is locked against regression via two artifacts.
   - Current: No coverage golden; HTML viewer (from 01-15) renders only legacy `ModelRecord` fields.
   - Target:
     - `server/tests/__snapshots__/bmw-pilot.test.ts.snap` locks the per-field-group coverage rates (rounded to 2 decimal places) for the BMW pilot run. Snapshot mismatch fails CI.
     - The per-run HTML viewer (from plan 01-15) is extended to render the new complectation fields. A golden screenshot of the BMW pilot's `current/index.html` (rendered headless, fixed viewport) is checked into `server/tests/__snapshots__/bmw-pilot-viewer.png`. Image diff > 0.5 % fails the test.
   - Acceptance: `pnpm test` runs the snapshot test against a captured BMW pilot fixture and the screenshot diff against the golden image; both pass.

## Boundaries

**In scope:**

- New parser `parse-complectation-page.ts` that handles one per-comp HTML page → `Complectation`
- New `Complectation` zod sub-schema; `ModelRecord` extended with `complectations: Complectation[]`
- Six field groups: identity, pricing, drivetrain, dimensions, comfort, tires (all nullable leaves)
- Drom orchestrator extension: per-comp fetch loop, BMW brand filter
- Probe-down rate limiter (10 s → 5 s, halve per 100 OK, reset on 429/block)
- BMW pilot run end-to-end (≈ 2 000 per-comp pages, ≈ 5–7 h continuous)
- `report.json.field_coverage` per-group metrics
- HTML viewer extension to render complectation fields
- Two golden artifacts: per-field coverage snapshot test + HTML viewer screenshot test

**Out of scope:**

- Multi-brand sweep beyond BMW — deferred to v1.x; rate-limit posture for a 50-brand sweep is unproven and would dominate the soft-launch deadline
- Average price aggregated from baza.drom.ru classifieds — separate scraper of a separate site with its own bot-detection profile and 152-FZ posture
- Drom partner-API spike (D-04 from `01-CONTEXT.md`) — kept deferred; this phase commits to scraping path
- Other scrapers (Encar / BeForward / Che168 / Autohome) — still stubs; this phase changes only the drom scraper
- DB import of complectations — Phase 03 (schema + importer)
- Continuous-cron scheduling of the per-comp sweep — Phase 02 (compliance & infra) covers cron infra; this phase ships a one-shot resume-aware run
- Translating tire spec strings into structured `width/aspect/diameter` — kept as raw strings; structured parsing deferred to v1.x

## Constraints

- Drom rate-limit floor is **5 s** under the probe-down rule. Hardcoded; do not add CLI override in this phase.
- Per-comp pages share the same block-detection and CAPTCHA fingerprints as catalog pages — reuse `shared/block-detection.ts` unchanged.
- The `Complectation` zod schema must be importable by Phase 03's importer without circular-dep issues — keep all complectation types in `server/scrapers/shared/types.ts`.
- BMW pilot run must complete on a single resume-aware orchestrator invocation (no manual restart). Cursor format from 01-16 (brand-root `.cursor.json`) extended only if needed; no breaking change.
- HTML viewer extension must remain self-contained (no external network requests at view time) — same constraint as plan 01-15.

- [ ] Drom orchestrator fetches per-comp pages **only** for BMW brand; non-BMW brands' generation handling is unchanged
- [ ] Probe-down rate limiter unit-tested: starts at 10 s, halves to 5 s after 100 OK, resets to 10 s on 429, never below 5 s
