# Phase 01.1: extend-drom-scrape-fields — Research

**Researched:** 2026-04-29
**Domain:** Per-complectation page parser + nested zod schema + adaptive rate limiter + screenshot golden (drom.ru/catalog deep-dive)
**Confidence:** HIGH (DOM structure verified live; tooling versions verified via npm registry; all six field groups confirmed against `https://www.drom.ru/catalog/bmw/x5/207354/`)

## Summary

Phase 01.1 is a **pure extension of an already-working scraper**, not a green-field build. The drom orchestrator (`server/scrapers/drom/index.ts`), the cheerio-+-zod parser pattern (`parse-generation-page.ts`), the cursor module (`shared/cursor.ts`), the polite HTTP client (`shared/http.ts`), the snapshot golden plumbing (`server/tests/__snapshots__/`), and the per-run HTML viewer (`shared/report-html.ts`) are all in place from Phase 01 plans 01..16. None of the eight SPEC.md requirements asks for new infrastructure — every R-N either adds a new module that mirrors an existing pattern, or extends an existing module by 5–40 lines.

The two material decisions left for the planner are tooling-shape: how to capture three live BMW per-comp fixtures (`--capture-fixture <comp_id>` flag added to the existing `server/scrapers/cli.ts`) and which library to use for the SPEC R-8 screenshot golden (`puppeteer-core@24.x` + `@sparticuz/chromium`-style local Chromium, OR `node-html-to-image` which wraps `puppeteer`, OR `playwright@1.59`). The recommended pick — **`puppeteer@24.42.0` directly + `pixelmatch@7.2.0` + `pngjs@7.0.0`** — is justified in §Standard Stack below.

The DOM structure of a per-comp page was confirmed by a live fetch of `https://www.drom.ru/catalog/bmw/x5/207354/` (xDrive 30d AT Base): every leaf in the SPEC's six field groups is present and rendered as a labelled spec line under Russian section headings (Габариты / Объемы / Кузов / Масса / Двигатель / Трансмиссия / Расход топлива / Шины и диски). Selector strategy is straightforward (label-text scan + sibling-cell read), with no JS hydration to wait on (confirmed: drom is mostly server-rendered HTML; existing parsers run on `got` + `iconv-lite`-decoded windows-1251 buffers).

**Primary recommendation:** Mirror the existing parser/test pattern verbatim for `parse-complectation-page.ts`, extract the probe-down state machine into its own pure-function module (`shared/rate-limiter.ts`) so it can be unit-tested without any HTTP, add `puppeteer` + `pixelmatch` + `pngjs` to devDependencies for one screenshot golden, and extend `cli.ts` with a `--capture-fixture <comp_id>` branch that writes one HTML file under `server/tests/fixtures/drom/complectation/`. Cursor schema gets one new optional field (`lastComplectationIndex`); `lastGenerationSlug` is **not** needed (rationale in §Architecture Patterns).

## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01 — Cursor extends to per-trim resolution.** Add `lastComplectationIndex: number | null` to `cursor.json` next to existing `lastBrandSlug` / `lastModelSlug`. On resume mid-generation, the per-comp loop skips already-fetched trims using the saved index. Worst-case refetch on a fresh resume is the trim that was in flight when the run died (≤ 1 page).

**D-02 — Cursor write cadence is every trim** (no throttling). The BMW pilot's ~2 000 trim writes are cheap (`writeFileSync` on a sub-1KB JSON), and the simpler invariant is worth the trivial I/O.

**D-03 — Crossing into a new generation resets `lastComplectationIndex` to 0** (or `null`); the existing `CursorSchema` (Phase 01-11) extension must remain backward-compatible — a cursor written by Phase 01 (without the index) loads as `lastComplectationIndex = null` and the per-comp loop starts from 0.

**D-04 (open for planner) — Whether `lastGenerationSlug` also needs to enter the cursor schema.** Today the cursor stops at brand+model — but the per-comp loop iterates trims of multiple generations within one model. **Researcher recommendation in §Architecture Patterns below: NO, `lastGenerationSlug` is not needed.** Reasoning: the orchestrator's per-comp loop is nested inside the per-generation loop, which is nested inside the per-model loop; on resume, the CR-04 contract from plan 01-12 already re-scrapes the cursored brand from scratch — adding generation-level resume state would conflict with that contract and is not justified by the BMW-pilot worst-case refetch (one model × all-its-generations × all-its-trims ≈ 2–4 generations × 30 trims × 5 s = 5–10 minutes, well below the cost of a new cursor field + zod migration + integration test).

**D-05 — Per-trim, majority-threshold coverage formula.** For each trim, a group is "covered" if **≥ ⌈2/3 × leaf_count⌉** of its leaves are non-null. The group's coverage is `count(covered trims) / total_trims`. Gate: each of the six groups ≥ 0.70 across the BMW pilot.

**D-06 — Threshold table** (precomputed; planner / verifier hardcodes from this list — no runtime ceil math):
- Identity (7 leaves)   → ≥ 5 non-null per trim
- Pricing (2 leaves)    → ≥ 2 non-null per trim (effectively all)
- Drivetrain (6 leaves) → ≥ 4 non-null per trim
- Dimensions (9 leaves) → ≥ 6 non-null per trim
- Comfort (6 leaves)    → ≥ 4 non-null per trim
- Tires (2 leaves)      → ≥ 2 non-null per trim (effectively all)

**D-07 — Pricing and Tires both collapse to "all leaves required"** because ⌈2/3 × 2⌉ = 2. This is intentional — for these two-leaf groups, partial extraction is not informative. If tire extraction in practice falls below 70% of trims, the planner should surface this as a SPEC.md adjustment request rather than silently weakening the formula.

**D-08 — `field_coverage` lives in `report.json`** as a top-level object next to existing `image_failure_rate`. Snapshot golden (`bmw-pilot.test.ts.snap` per SPEC R-8) locks the six rates rounded to 2 decimal places.

### Alternatives Considered (and why rejected for THIS phase)

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| `puppeteer` | **`playwright@1.59.1`** [VERIFIED: registry] | Heavier (~280–300 MB Chromium + WebKit + Firefox auto-install); CLAUDE.md flags it as project-approved for future Encar/Che168 phases needing fingerprint randomisation. **For THIS phase**: 1 file:// HTML render + 1 PNG screenshot, no anti-bot, no JS hydration to wait on. Playwright's full browser fleet is wasted; introduce it in v1.x when an Encar/Che168 scraper actually needs it. |
| `puppeteer` | **`node-html-to-image@5.0.0`** [VERIFIED: registry] | Adds an indirection (calls `puppeteer-core` under the hood per its npm README). The wrapper gains us nothing — we have one HTML file and want one PNG; calling `page.setContent()` + `page.screenshot()` directly is 8 lines. The wrapper also pins to puppeteer-core which forces us to manage Chromium download separately. |
| `puppeteer` | **`sharp@0.34.5` (already in deps) for rendering** | Rejected: sharp encodes/decodes/resizes images but cannot **render HTML** to a raster — there is no rendering engine. sharp IS valid as the comparator IF we want to skip pixelmatch (sharp can compute pixel diffs via `image1.composite(image2, {blend: 'difference'})` + statistics), but pixelmatch is more battle-tested for this exact use case and the dep cost is trivial (~150 LOC, no transitives). |
| `puppeteer` | **`html-pdf-chrome` / `dom-to-image`** | Both are HTML→image, but both are unmaintained or browser-side-only; rejected on currency. |

**Decision rationale (puppeteer over playwright for THIS phase):**

1. **Surface area minimisation.** SPEC R-8 needs one PNG of one local HTML file. Puppeteer's `chromium.launch() → page.setContent(html) → page.screenshot()` is the minimum viable.
2. **Future migration path is mechanical.** If Phase 02+ wants Playwright for live-site UAT, the screenshot golden can be re-pointed at `playwright`'s `chromium` API in ~10 lines (same `page.setContent()` + `page.screenshot()` semantics).
3. **CLAUDE.md does pin Playwright** as the project's eventual scraping toolchain for Encar/Che168, but **Phase 01-D-03** [VERIFIED: `01-CONTEXT.md` line 31] explicitly **scoped Phase 01 down** to `got-scraping + cheerio + sharp` because drom is RU-domestic, public, and static. The same logic applies here: don't pull Playwright's full machinery for a deterministic file:// render.
4. **The screenshot is `current/index.html` rendered headless with fixed viewport** — a deterministic, isolated artifact. No real-network, no JS interaction. Puppeteer is sufficient.

### Pattern 1: cheerio + zod parser, fail-soft variant

**What:** Each per-comp parser function wraps its DOM scan in `try/catch`, returning `null` for the entire group on any failure (selector miss, type coercion error, zod safeParse fail). The full record is then passed through `Complectation.safeParse()` — on schema mismatch, return the all-null shape with `_extraction_errors[]`.

**When to use:** Phase 01.1 inverts Phase 01's "throw loudly" parser pattern (Pitfall 1) at the per-comp boundary, because the SPEC explicitly says no field is must-have. The throw-loudly pattern is preserved on the **generation** parser; only the new per-comp parser is fail-soft.

**Example (skeleton):**
```typescript
// Source: SPEC R-6 + existing pattern in parse-generation-page.ts
function extractDimensions($: cheerio.CheerioAPI): Dimensions | null {
  try {
    return {
      length_mm: numFromLabel($, 'Длина, мм'),
      width_mm: numFromLabel($, 'Ширина, мм'),
      height_mm: numFromLabel($, 'Высота, мм'),
      wheelbase_mm: numFromLabel($, 'Колесная база, мм'),
      clearance_mm: numFromLabel($, 'Дорожный просвет, мм'),
      trunk_min_l: trunkMinFromLabel($, 'Объем багажника, л'),
      trunk_max_l: trunkMaxFromLabel($, 'Объем багажника, л'),
      curb_weight_kg: numFromLabel($, 'Снаряженная масса, кг'),
      gross_weight_kg: numFromLabel($, 'Максимальная допустимая масса, кг'),
    };
  } catch {
    return null; // entire group is null; never throws
  }
}
```

### Pattern 2: Pure state machine + thin wrapper (rate limiter)

**What:** Extract the probe-down algorithm into `shared/rate-limiter.ts` as a pure class with `onResponse(statusCode)` / `onBlock()` / `getDelayMs()`. The HTTP wrapper in `shared/http.ts` becomes thin: it asks the limiter for delay, sleeps, fires the request, and feeds the response status back to the limiter.

**When to use:** SPEC R-5 acceptance requires unit-test simulation of "100 OK responses" — only feasible if the state machine is pure. Mirrors how block-detection is already split (`shared/block-detection.ts` is pure logic; orchestrator inspects responses).

**Example:** See §Code Examples "Probe-down state machine".

### Pattern 3: Nested orchestrator extension with brand allow-list

**What:** A constant `BMW_PILOT_BRANDS = new Set(['bmw'])` at the top of `drom/index.ts`. The per-comp loop is gated by an `if (BMW_PILOT_BRANDS.has(brand.brand_slug))` block. Other brands' generation handling is unchanged — the new code is strictly additive.

**When to use:** Phase 01-D-03 already established the `DROM_BRAND_WHITELIST` env var for runtime smoke gates. Phase 01.1's BMW filter is a *static* compile-time constant that is **independent** of the env var. The two filters compose: env var filters which brands the orchestrator visits at all; the BMW set filters which visited brands get per-comp deep-dive. Phase 01-CONTEXT.md "code_context" line 94 confirms: "No existing pattern for 'scrape only some brands'. Plan-phase introduces an explicit brand allow-list."

### Pattern 4: Coverage formula as pure function over the seen-map

**What:** `computeFieldCoverage(records: ModelRecord[]): FieldCoverage` lives in `shared/coverage.ts`. Reads `records.flatMap(r => r.complectations)`, evaluates the precomputed thresholds (D-06: 5/2/4/6/4/2 leaves), divides by `total_trims`, rounds to 2 decimal places. Called once at the end of the orchestrator after all records are merged into `seen`.

**Why pure:** Unit-testable without orchestrating a full run. Snapshot golden against three synthetic trim sets (one all-populated, one half-broken, one threshold-edge) gives full coverage of D-06.

### D-04 resolution: cursor schema does NOT need `lastGenerationSlug`

**Reasoning (verified against `server/scrapers/drom/index.ts` lines 333–412):**

The orchestrator's nested loop is `brand → model → generation → trim`. The Phase 01 cursor checkpoints `(brand, model)` after every model finishes (line 407). Plan 01-12 / CR-04 contract pinned: when resume reads a cursor with `lastBrandSlug = X`, brand X is **re-scraped from scratch** (i.e., `startFromModelIndex = 0`), with the prior `current/` snapshot's records preserved by `inheritFromPrevCurrent` for OTHER brands.

For Phase 01.1, mid-model resume cost is bounded by:
> 1 model × all-its-generations × all-its-trims = 2–4 generations × ~30 trims × 5–10 s polite delay = 5–20 minutes refetch

This is below the cost of:
- a new `lastGenerationSlug` field in `CursorSchema` (zod migration risk + backward-compat handling)
- a new `findIndex(g => g.generation_id >= cursor.lastGenerationSlug)` block + cursor-drift throw
- a new integration test for "cursor points at a generation that no longer exists"

Adding generation-level resume state would also **conflict with the CR-04 contract** that the cursored brand is re-scraped from scratch — generation-level skipping would break that invariant or require yet another conditional gate.

**Recommendation:** Cursor extends only with `lastComplectationIndex: number | null` (D-01..D-03). On resume, when the cursored brand's cursored model is reached, the orchestrator iterates ALL its generations from index 0 and ALL their trims from index 0, but for the **specific generation** that contains `lastComplectationIndex` (i.e., the one whose trim list hadn't completed), it skips trims with index < `lastComplectationIndex`. Because a model's generations have disjoint trim lists, the index is unambiguous within the in-flight generation — no `lastGenerationSlug` needed.

Even simpler implementation (recommended for the planner): on resume, **re-fetch every trim of every generation of the cursored model**. The worst-case refetch is a single model (5–20 minutes); the cursor's `lastComplectationIndex` then only matters for the in-flight generation, not for already-completed-then-restarted ones. This matches the spirit of the CR-04 contract (the cursored unit is re-scraped from scratch; only finer-grained units within it use the cursor for fast-forward).

### Anti-Patterns to Avoid

- **Adding a runtime CLI flag for the rate-limit floor.** SPEC C-1 explicitly hardcodes 5s; deferred to follow-up phase.
- **Hand-rolling a "wait for X consecutive successes" via fixed-window counters that reset incorrectly on race conditions.** Use a single integer counter inside the pure limiter class; mutate only inside `onResponse()`. No timers, no setIntervals.
- **Passing the full HTML through to the orchestrator and parsing trim rows there.** The trim-row extraction belongs IN `parseGenerationPage` (or a new `extractTrimRows` exported alongside it) — the orchestrator should consume a typed `TrimRowRef[]`, not raw HTML.
- **Treating `_extraction_errors[]` as a `report.errors[]` substitute.** Those are TWO different telemetry channels: `_extraction_errors[]` is per-record annotation (which group failed); `report.errors[]` is run-wide event log (with `kind: 'parse'`). The SPEC R-6 acceptance requires BOTH.
- **Embedding the coverage formula inline in `report-html.ts` for display.** Coverage computation belongs in `shared/coverage.ts`; viewer only reads `report.field_coverage`.
- **Loading the full BMW pilot dataset into the snapshot golden test.** SPEC R-8 says snapshot locks the **rates** (six numbers), not the records. Use a fixture-driven mini-pilot (3 trims) for `bmw-pilot.test.ts`.

## Common Pitfalls

### Pitfall 1: "Pitfall 1 inversion" at the parser boundary

**What goes wrong:** The Phase 01 catalog parser (`parse-generation-page.ts`) throws on zod failure as the DOM-regression detector. If the per-comp parser inherits this pattern, a single broken section on one trim aborts the whole BMW pilot.

**Why it happens:** Copy-paste of the existing parser pattern feels right; the inversion is non-obvious unless SPEC R-6 is read carefully.

**How to avoid:**
- Use `Complectation.safeParse()` instead of `.parse()`.
- Wrap each `extract<Group>()` in `try/catch` returning `null`.
- The orchestrator's existing 10% parse-error abort gate (line 426) is gated on `kind: 'parse'` — per-comp failures should push to `report.errors[]` with `kind: 'parse'` BUT the per-comp record itself must still be emitted with null leaves. The existing 10% gate then meaningfully trips ONLY if catastrophic numbers of generation-level parses fail; per-comp parses are bounded by their own 70% coverage gate (R-7), not by the 10% parse-error gate.

**Warning signs:** A unit test against a fixture with a deliberately broken `<table>` returns a thrown exception → bug.

### Pitfall 2: Hashed CSS class names rotate on deploy

**What goes wrong:** Selectors like `.r6hmq22` or `.y7l57t0` (used in `parse-generation-page.ts`) are vanilla-extract-style content hashes. Drom can deploy-rotate them and break the scraper without notice.

**Why it happens:** These are not human-authored class names; the build pipeline regenerates them.

**How to avoid:**
- Prefer label-text scans for new per-comp selectors: `$('span:contains("Длина, мм")').parent().find('.value').text()` or similar.
- Where class-based selectors are unavoidable (because the page has no labelled structure), document them with a "may rotate on drom deploy" comment AND back them with a fallback regex on raw HTML.
- The unit test for each extract function MUST also accept a hand-edited fixture with the class name munged — pinning that the fallback path works.

**Warning signs:** Unit tests pass against the captured fixture but the live BMW pilot returns 0% coverage on a group whose extractor uses class selectors.

### Pitfall 3: Trunk volume is a paired (min, max) number in one cell

**What goes wrong:** Live confirmation showed `Объем багажника, л: 645 (1860)` — i.e., min volume with seats up, max with seats folded, in a single cell. A naive `parseInt(text)` extracts only `645` and silently drops `trunk_max_l`.

**Why it happens:** No labelled split between min/max; the formatting is `<min>(<max>)` or `<min> (<max>)`.

**How to avoid:** Regex parse of the full cell text: `/(\d+)\s*\(?\s*(\d+)?\s*\)?/`. If second group missing → `trunk_max_l = null`. Three captured fixtures (xDrive 30d, xDrive 30d M Sport Plus, M Competition) MUST cover the case where only one number is present (some compact trims don't list the folded volume).

**Warning signs:** `trunk_max_l` is null on every record despite the BMW pilot.

### Pitfall 4: Per-comp page doesn't always carry every section

**What goes wrong:** The base trim shows full Габариты + Объемы + Расход топлива. Premium trims sometimes substitute a "Технические характеристики" custom layout that omits Расход топлива (presumably because the manufacturer doesn't publish official figures). Over the BMW pilot, 5–15 % of trims may legitimately have ≤ 1 fuel-consumption leaf.

**Why it happens:** Manufacturer-side data heterogeneity.

**How to avoid:** Confirms the SPEC's "no must-have fields" choice. The 70 % per-group threshold is **across all trims**, not per trim — D-05 formula explicitly counts trims that meet the per-trim threshold. A trim missing 2 of 6 comfort leaves still "covers" the comfort group (4/6 ≥ ⌈2/3 × 6⌉ = 4).

**Warning signs:** Coverage gate fails on Comfort with rate ≈ 0.65; investigation shows a specific trim cluster (e.g., M Competition variants) consistently lacks `fuel_consumption_*`. Action: SPEC adjustment (D-07 escalation), not formula weakening.

### Pitfall 5: Probe-down counter races on retry

**What goes wrong:** got's retry config (`retry.limit: 3` for 408/429/5xx) means a single 429 triggers up to 4 HTTP attempts. If the limiter feeds every attempt's status into `onResponse()`, the consecutive-OK counter is mis-decremented on the (retried-and-recovered) success.

**Why it happens:** Retry happens inside `got`; the polite-delay layer is above it; the limiter sees only the FINAL response.

**How to avoid:** Keep `onResponse(finalStatus)` called exactly once per `fetchHtml()` invocation, with the final status. Internally retried 429s show up as one event (the final 200 OK if retry succeeded, or the final 429 if retry exhausted). This is implicitly correct given the existing `dromClient.get(...)` shape — the retry happens before our wrapper observes the result.

**Warning signs:** Unit test simulating "100 OKs" passes but live pilot's delay never halves because each "real" response actually involved a 429-then-retry that the limiter mis-counted.

### Pitfall 6: Snapshot non-determinism from `runId` in viewer HTML

**What goes wrong:** `report-html.ts` embeds the runId (an ISO timestamp) into the rendered HTML. A screenshot golden of `current/index.html` would diff every run.

**Why it happens:** The runId is timing-sensitive metadata; the viewer prints it in the header.

**How to avoid:** The screenshot test invokes `writeReportHtml(tmpDir, {models: fixtureRecords, report: fixtureReport})` with a **fixed-name run** (e.g., `data/scraped/drom/test-fixture-Z`) and a **fixed `started_at`/`finished_at`** in the fixture report. The existing `report-html.test.ts` snapshot does exactly this (per 01-15-SUMMARY.md "snapshot test uses opts override + a fixed-name sub-dir to keep the runId portion of the HTML deterministic"). Re-use that pattern.

**Warning signs:** First run of the screenshot test passes; second run fails with diff > 0.5 % on text-only pixels (the timestamp).

### Pitfall 7: Headless Chromium font rendering varies CI vs local

**What goes wrong:** macOS dev box renders Helvetica/SF Pro from `-apple-system` font stack; Linux CI Chromium falls back to DejaVu Sans. Pixel diff is ~5–10 % on text-heavy pages.

**Why it happens:** The viewer's CSS uses a system-font stack: `font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", "Helvetica Neue", Arial, ...`.

**How to avoid:**
- **Option A (recommended):** Force a single explicit font by injecting a `<style>` override in the test before screenshot: `* { font-family: 'DejaVu Sans', sans-serif !important; }`. Both macOS Chromium and Linux Chromium ship DejaVu Sans (Chromium bundles it). Result: identical rendering.
- **Option B:** Run the screenshot test only in Linux CI; on macOS dev, mark it `it.skipIf(!process.env.CI)`. Trade: lose dev-time regression catch.
- **Option C:** Use `puppeteer.launch({ args: ['--font-render-hinting=none'] })` and a `<style>` that pins fonts to a Chromium-bundled family. Less hacky than Option A.

**Warning signs:** Snapshot passes on `npm test` but fails the moment the test moves to GitHub Actions / GitLab CI runner.

### Pitfall 8: `_extraction_errors[]` annotation breaks Phase 03 zod consumption

**What goes wrong:** The fail-soft parser adds a `_extraction_errors: { group: string; message: string }[]` field to the record for observability. If `Complectation.safeParse()` is strict (`z.object` defaults to passthrough-strip), this field is silently dropped — but if Phase 03's importer uses a different parser config, it could trip.

**Why it happens:** Zod's default behaviour (`z.object().strict()` would reject; `z.object().passthrough()` would keep) is unintuitive.

**How to avoid:**
- Define `Complectation` with explicit `_extraction_errors: z.array(...).optional()` in the schema.
- Documentation comment: "_extraction_errors is a Phase 01.1 telemetry annotation; Phase 03 importer ignores it but the field is part of the canonical schema."

**Warning signs:** Phase 03 importer's first DB write rejects records with an "unknown field" error.

//
// Verified via live fetch of /catalog/bmw/x5/207354/ — see RESEARCH.md.
// Each extract<Group>() catches its own failures and returns null on any miss.

import * as cheerio from 'cheerio';
import type { Complectation, TrimRowRef, ModelRecord } from '../shared/types.js';

/**
 * Find the value cell for a Russian label. Drom renders specs as
 * <h3>Heading</h3>
 *   <table>
 *     <tr><td>Длина, мм</td><td>4922</td></tr>
 *     ...
 * The label-cell selector is text-content based to survive class-name rotation.
 */
function valueByLabel($: cheerio.CheerioAPI, label: string): string | null {
  const labelCell = $('td, th, span, dt')
    .filter((_, el) => $(el).text().trim() === label)
    .first();
  if (labelCell.length === 0) return null;
  // Try sibling td (table layout), then sibling dd, then parent's next-sibling.
  const value =
    labelCell.next('td, dd, span').text().trim() ||
    labelCell.parent().next().text().trim();
  return value || null;
}

function numFromLabel($: cheerio.CheerioAPI, label: string): number | null {
  const raw = valueByLabel($, label);
  if (!raw) return null;
  const m = raw.match(/(-?\d+(?:[.,]\d+)?)/);
  if (!m) return null;
  const n = Number(m[1].replace(',', '.'));
  return Number.isFinite(n) ? n : null;
}

/** "645 (1860)" → { min: 645, max: 1860 }; "645" → { min: 645, max: null } */
function trunkRange($: cheerio.CheerioAPI): { min: number | null; max: number | null } {
  const raw = valueByLabel($, 'Объем багажника, л');
  if (!raw) return { min: null, max: null };
  const m = raw.match(/(\d+)\s*\(?\s*(\d+)?\s*\)?/);

  return {
    min: Number(m[1]),

### Probe-down state machine (pure module, fake-timer testable)

```typescript
// server/scrapers/shared/rate-limiter.ts (NEW)
//
// SPEC R-5: start delay=10s; halve every 100 OK responses to floor 5s;
// reset to 10s on any 429/5xx/block-detection match.
// Pure state machine — no side effects, no timers. The HTTP wrapper is
// responsible for actually sleeping `getDelayMs()` ms before each request.

const FLOOR_MS = 5_000;
const CEIL_MS = 10_000;
const HALVE_AFTER_OK = 100;

export class ProbeDownLimiter {
  private delayMs = CEIL_MS;
  private consecutiveOk = 0;

  /** Current polite delay between sequential requests, in milliseconds. */
  getDelayMs(): number {
    return this.delayMs;
  }

  /** Feed every request's final response status. Internally retried 429s show up
   *  as one event (the final status post-retry). */
  onResponse(statusCode: number): void {
    if (statusCode === 429 || (statusCode >= 500 && statusCode < 600)) {
      this.delayMs = CEIL_MS;
      this.consecutiveOk = 0;
      return;
    }
    if (statusCode >= 200 && statusCode < 300) {
      this.consecutiveOk++;
      if (this.consecutiveOk >= HALVE_AFTER_OK) {
        this.delayMs = Math.max(FLOOR_MS, Math.floor(this.delayMs / 2));
        this.consecutiveOk = 0;
      }
      return;
    }
    // 3xx, 4xx (except 429), or other unexpected: do nothing (delay unchanged).
  }

  /** Reset on block-detection match (captcha keywords, thin responses). */
  onBlock(): void {
    this.delayMs = CEIL_MS;
    this.consecutiveOk = 0;
  }
}
```

```typescript
// server/scrapers/shared/http.ts (REPLACEMENT for politeDelay)
import { ProbeDownLimiter } from './rate-limiter.js';

const limiter = new ProbeDownLimiter();
const JITTER_RATIO = 0.20;
let lastRequestAt = 0;

export async function politeDelay(): Promise<void> {
  const baseMs = limiter.getDelayMs();
  const elapsed = Date.now() - lastRequestAt;
  const jitter = baseMs * (1 + (Math.random() * 2 - 1) * JITTER_RATIO);
  const wait = Math.max(0, jitter - elapsed);
  if (wait > 0) await new Promise((r) => setTimeout(r, wait));
  lastRequestAt = Date.now();
}

export async function fetchHtml(url: string): Promise<string> {
  return httpLimit(async () => {
    await politeDelay();
    const response = await dromClient.get(url, { responseType: 'buffer' });
    limiter.onResponse(response.statusCode);
    const charset = charsetFromContentType(response.headers['content-type']);
    return iconv.decode(response.body as Buffer, charset);
  });
}

// Block-detection integration (orchestrator already calls detector.inspect):
// expose limiter.onBlock() so the orchestrator's BlockedError-throwing path
// can also reset the delay. Optional — not strictly required by SPEC since
// the run aborts anyway, but useful for the Phase 02 cron-resume case.
export const _testOnly = { limiter };

  identity: 5,    // 7 leaves, ≥5 non-null
  pricing: 2,     // 2 leaves, ≥2 non-null (all)
  drivetrain: 4,  // 6 leaves, ≥4 non-null
  dimensions: 6,  // 9 leaves, ≥6 non-null
  comfort: 4,     // 6 leaves, ≥4 non-null
  tires: 2,       // 2 leaves, ≥2 non-null (all)
} as const;

type GroupKey = keyof typeof THRESHOLDS;

export interface FieldCoverage {
  identity: number;
  pricing: number;
  drivetrain: number;
  dimensions: number;
  comfort: number;
  tires: number;
}

function nonNullLeafCount(group: Record<string, unknown> | null): number {
  if (group === null) return 0;
  return Object.values(group).filter((v) => v !== null).length;
}

function trimMeetsThreshold(comp: Complectation, group: GroupKey): boolean {
  return nonNullLeafCount(comp[group] as Record<string, unknown>) >= THRESHOLDS[group];
}

export function computeFieldCoverage(records: ModelRecord[]): FieldCoverage {
  const trims = records.flatMap((r) => r.complectations);
  const total = trims.length;
  if (total === 0) {
    return { identity: 0, pricing: 0, drivetrain: 0, dimensions: 0, comfort: 0, tires: 0 };
  }

  const round2 = (n: number) => Math.round(n * 100) / 100;

  return {
    identity: round2(trims.filter((t) => trimMeetsThreshold(t, 'identity')).length / total),
    pricing: round2(trims.filter((t) => trimMeetsThreshold(t, 'pricing')).length / total),
    drivetrain: round2(trims.filter((t) => trimMeetsThreshold(t, 'drivetrain')).length / total),
    dimensions: round2(trims.filter((t) => trimMeetsThreshold(t, 'dimensions')).length / total),
    comfort: round2(trims.filter((t) => trimMeetsThreshold(t, 'comfort')).length / total),
    tires: round2(trims.filter((t) => trimMeetsThreshold(t, 'tires')).length / total),
  };
}

// Gate (called by the orchestrator before declaring final_status='ok'):
export function meetsCoverageGate(coverage: FieldCoverage): boolean {
  return (Object.values(coverage) as number[]).every((rate) => rate >= 0.70);
}
```
