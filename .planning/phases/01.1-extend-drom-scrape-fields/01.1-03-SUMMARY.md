## Implementation Details

### rate-limiter.ts (54 LOC)

Pure state machine class with:
- `getDelayMs()` — returns current delay (starts 10000ms)
- `onResponse(statusCode)` — feeds final post-retry HTTP status; 2xx increments consecutive-OK counter; at 100 consecutive OKs, halves delay (floor 5000ms, then no further halving); 429/5xx resets to 10000ms and clears counter; 3xx/other 4xx are no-ops
- `onBlock()` — resets delay to 10000ms and clears counter (for BlockDetector integration)
- `get consecutiveOkCount` — test-only getter mirroring BlockDetector.consecutiveThin

Zero imports, zero timing primitives.

### http.ts edits (4 changes)

1. **Import added** (line 18): `import { ProbeDownLimiter } from './rate-limiter.js';`
2. **politeDelay replaced** (lines 23-44): `const limiter = new ProbeDownLimiter()` replaces `const POLITE_BASE_MS = 10_000`; `politeDelay()` reads `const baseMs = limiter.getDelayMs()` instead of the deleted constant
3. **fetchHtml feed** (line 79): `limiter.onResponse(response.statusCode)` inserted after `dromClient.get()` return — Pitfall 5 invariant: got's internal retry runs inside `.get()`, so this line sees the FINAL post-retry status
4. **_testOnly export** (line 95): `export const _testOnly = { limiter }` for Plan 07 integration wiring

### dromClient retry config — UNCHANGED

The `dromClient.extend()` retry block (`limit: 3, statusCodes: [408, 429, 500, 502, 503, 504], calculateDelay: exponential`) was not modified. This is the Pitfall 5 invariant: got folds all per-attempt retries inside `.get()`, and `limiter.onResponse()` always sees exactly one final status per `fetchHtml()` call.
