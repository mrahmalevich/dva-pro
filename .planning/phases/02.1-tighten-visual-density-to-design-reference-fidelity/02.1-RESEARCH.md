- **Top contributor #2 — `section { padding: 140px 0 }` × 7 sections:** 280 px of vertical padding × 7 ID'd sections (`#catalog`, `#process`, `#founders`, `#lead-magnet`, `#reviews`, `#faq`, plus the hero's `paddingTop: 140` inline) = 1 960 px of pure padding. import puppeteer from 'puppeteer';
const VIEWPORT = { width: 1280, height: 1080 };
const DEV_URL = 'http://127.0.0.1:5174/';
const browser = await puppeteer.launch({
  headless: true,
  args: ['--font-render-hinting=none', '--disable-font-subpixel-positioning'],
});
try {
  const page = await browser.newPage();
  await page.setViewport({ ...VIEWPORT, deviceScaleFactor: 1 });
  await page.goto(DEV_URL, { waitUntil: 'networkidle0', timeout: 30_000 });
  // Force every Reveal IntersectionObserver to fire by scrolling end-to-end.
  await page.evaluate(async () => {
    const total = document.documentElement.scrollHeight;
    for (let y = 0; y < total; y += 800) { window.scrollTo(0, y); await new Promise(r => setTimeout(r, 60)); }
    window.scrollTo(0, 0);
  });
  await new Promise(r => setTimeout(r, 1500));
  const result = await page.evaluate(() => {
    const body = document.body;
    const total = Math.max(body.scrollHeight, document.documentElement.scrollHeight);
    const seen = new Set(); const ordered = [];
    for (const el of [
      document.querySelector('header#top'),
      ...document.querySelectorAll('section'),
      document.querySelector('footer'),
    ]) { if (el && !seen.has(el)) { seen.add(el); ordered.push(el); } }
    const rows = ordered.map(el => {
      const r = el.getBoundingClientRect();
      const cs = window.getComputedStyle(el);
      const heading = el.querySelector('h1, h2, h3, .h1, .h2, .h3, .h-display, .h-mega');
      return {
        tag: el.tagName.toLowerCase(),
        id: el.id || '(none)',
        heading: heading ? heading.textContent.trim().slice(0, 60) : '(no heading)',
        height: Math.round(r.height),
        padTop: Math.round(parseFloat(cs.paddingTop) || 0),
        padBot: Math.round(parseFloat(cs.paddingBottom) || 0),
        minHeight: cs.minHeight,
        contentHeight: Math.round(r.height - (parseFloat(cs.paddingTop) || 0) - (parseFloat(cs.paddingBottom) || 0)),
      };
    });
    return { bodyTotal: Math.round(total), sections: rows };
  });
  console.log(JSON.stringify(result, null, 2));
} finally {
  await browser.close();
}

## 5. Predicted Post-Densification Math

Starting from real-device measurement of **8 927 px** at viewport 1280×1080.

### Lever 1 — `section { padding: 140px 0 }` → `padding: 72px 0`

Cascades to 6 sections (`#catalog`, `#process`, `#founders`, `#lead-magnet`, `#reviews`, `#faq`) — each saves 2 × (140 − 72) = 136 px. Total: **6 × 136 = 816 px saved**.

[Note: D-02 lower bound is `64px 0`. `72px 0` chosen because `72` is a documented spacing token (`5xl/2 = 72`, multiple of 4) and gives slightly more breathing room than `64`. `80px 0` is too loose given the target band. `64px 0` is acceptable if planner finds 72 still over-budget, BUT 64 is already the mobile `!important` value at line 598 — desktop and mobile would converge, removing the responsive rhythm distinction. **Recommend `72px 0`.**]

### Lever 2 — Hero `min-height: 100vh` → `min-height: 640px` + `paddingTop: 140 → 72`

At viewport 1080: `min-height: 100vh` resolves to 1 080 px; current hero rendered at 1 080 (the min-height is the binding constraint, not content height). New `min-height: 640` produces hero height = max(640, content height + paddingTop). Hero content is roughly 940 px tall (= 1 080 − 140 paddingTop − 0 paddingBottom). With `paddingTop: 72` the natural content stack is 940 + 72 = 1 012 px — already exceeds 640, so `min-height: 640` becomes a NON-binding lower bound and the actual hero height becomes the content stack: ~1 012 px.

Delta: 1 080 → 1 012 = **68 px saved on real device**.

## 8. Risks and Unknowns

### R-1 — Sticky/fixed Nav behavior with smaller hero

**Risk:** `Nav` (`src/components/Nav.tsx:35-41`) is `position: fixed`, frosted-on-scroll past 16 px. With `min-height: 100vh` removed and Hero shrinking to ~1 012 px, nav-state-transition trigger doesn't change (still 16 px scroll), so nav goes opaque much sooner relative to total page length. Visually: Nav frost activates within first ~1.6% of page scroll vs Phase 2's ~0.13%. **Likely fine** — nav feels responsive — but it's a perceived behavior change. **Verification:** Wave 2's golden test catches this only if the nav's frosted background + line color materially change in the squashed capture; manual visual inspection at three scroll positions (0, 200, 1200) recommended at Wave 2 close.

### R-2 — Section background alternation rhythm

**Risk:** Section backgrounds alternate between `var(--ink)` (#0A0A09) and `#0a0a09` (literally identical RGB values; visual separation comes from `var(--line)` borders). With section padding cut to 72, bordering-section line transitions sit closer together. **Acceptable** — UI-SPEC §Surface Treatments confirms borders are intentional rhythm anchors, not background contrast. No mitigation needed; just don't accidentally remove `border-top` / `border-bottom` from any section during tightening.

### R-3 — `Reveal` IntersectionObserver fires at faster scroll

**Risk:** With page 33% shorter (in capture terms) and ~13% shorter (in real-device terms), user scroll passes the 0.12 IntersectionObserver threshold faster. `Reveal` opacity transition is 1 s (UI-SPEC §Animation). At fast scroll, several sections' Reveal animations may be in flight simultaneously, which may visually feel like "everything fades in at once" rather than "section by section reveal." **Mitigation:** the 1500 ms settle in `landing-page-golden.test.ts:54` is unaffected — the test always waits for full-settle before capturing. Real-user perception is a UX consideration, NOT a test failure. **Recommend:** monitor at Wave 2 close; if the rhythm feels broken, file as Phase 8 polish (per D-04b — single revertable commit pattern allows surgical fix).

### R-4 — Counter timing relative to Reveal

**Risk:** `Counter` count-up duration is 1800 ms (UI-SPEC §Animation). Hero's stats Counter starts on Reveal-fire, which fires when stats strip enters viewport. At smaller hero, stats may be in viewport on initial paint (no scroll needed) — Counter starts immediately. The 1500 ms settle in the golden test is < 1800 ms, so counters render at ~83% of final value. THIS IS UNCHANGED FROM PHASE 2 — the same ratio holds. **No action needed.**

### R-5 — Mobile breakpoint VERIFICATION

**Risk:** D-04a explicitly forbids touching `@media (max-width: 720px)` rules. **VERIFIED:** the rules at `global.css:235`, `:567-650`, `:584-588` (mobile hero override) are mobile-gated; planner edits to line `:234` (canonical desktop section padding) and `Hero.tsx:37` (inline desktop hero) leave the mobile gates untouched. **Wave 2 close plan MUST grep-assert** that no `@media (max-width: 720px)` block was modified across the Phase 02.1 commit range. Concrete test: `git diff <phase-02.1-base>..HEAD -- src/styles/global.css | grep -E '^[+-].*@media|max-width: 720'` should return zero lines unless those lines are pure context.
