## Summary

Phase 02.1 ships a small, surgical visual-density tightening: six numeric paddings/margins/gaps are reduced across `Catalog`, `Founders`, `Hero`, `Process` and `global.css`; `Hero` swaps `min-height: 100vh` for `min-height: 640` (px) and reduces `paddingTop: 140 → 72`; the screenshot-diff golden test threshold lifts 0.22 → 0.28 with the dev port moved 5173 → 5174 (matching `vite.config.ts:6`); `.gitignore` adds `tmp/` and a base-sha exclusion. The findings below concentrate on three areas the diff legitimately touches: (1) the new fixed-px hero floor and its responsive interaction with the unchanged ≤720px override, (2) self-consistency of test metadata that the threshold-lift introduced, and (3) two pre-existing patterns that the phase migrates forward unchanged but are worth flagging because the diff drew attention to them.

## Warnings

### WR-01: Hero `min-height: 640` produces visible black gutter on tall desktop viewports

**File:** `src/sections/Hero.tsx:37`
**Issue:** The hero floor changed from `minHeight: '100vh'` to `minHeight: 640` (px). On any desktop viewport where the actual content height ends below the viewport bottom — which it now will on common 1440×900 / 1920×1080 / ultrawide / Yandex Browser fullscreen sessions, since 640 px is well under typical inner heights — the hero stops painting its dark background and the next section (`Catalog`, `var(--ink)`) abuts it. Because `Catalog` and `Hero` happen to share `var(--ink)` today, the seam is invisible *right now*, but:

  1. Any future change to a section background colour (e.g. moving to a paper section after Hero, which is contemplated in the design system — `--paper`/`--paper-2` variables exist in `global.css:38-39`) will reveal an abrupt color cut where users previously saw a full hero.
  2. The two absolutely-positioned background layers (`Hero.tsx:42-58`, the Unsplash photo + dual gradients + coral glow) are clipped to the hero's box. Reducing the hero from `100vh` to 640 px shrinks the visible "atmospheric" area users see before scrolling, which is a real UX/perceived-quality regression on >900 px viewports — not just a structural one.

The phase's stated goal is *density*, not "make hero shorter than viewport." A pixel floor that's smaller than every supported desktop viewport effectively removes the floor on desktop.

**Fix:** Use a viewport-aware floor that still permits densification but doesn't undershoot every desktop:
```tsx
// Hero.tsx:37
style={{ position: 'relative', minHeight: 'min(100vh, 760px)', background: 'var(--ink)', color: '#fff', overflow: 'hidden', paddingTop: 72 }}>
```
or a `clamp()` floor (`clamp(640px, 90vh, 900px)`) if the design intent is "tall but capped." Either preserves the densification win on short viewports (where 640 is the active floor) without leaving a black gutter on the desktop majority. If the visible regression is acceptable per design intent, document the rationale in the inline comment so the next maintainer doesn't "fix" it back to `100vh`.

### WR-02: Mobile override `header[class*="grain"] { min-height: auto !important; padding-top: 100px !important }` now fights a 640-px floor it was originally written against `100vh`

**File:** `src/styles/global.css:584-588`
**Issue:** The mobile breakpoint at `@media (max-width: 720px)` forces `min-height: auto !important` and `padding-top: 100px !important` on `header[class*="grain"]`. This was correct when the inline style was `minHeight: '100vh'` (the override collapsed the viewport-tall hero on small screens). Now that the inline style is `minHeight: 640` px, the override still wins (`!important` beats inline-style specificity for non-`!important` inline rules), so behavior on phones is unchanged — *but the override's purpose is no longer obvious*. A future engineer reading `min-height: auto !important` will not understand why it's needed when the desktop value is "only" 640 px, and is likely to delete it as redundant. That deletion would re-introduce a 640-px floor on a 360×640-class portrait phone where the URL bar already eats height, producing an awkward almost-but-not-quite-full-screen hero on first paint.

Additionally, the `padding-top: 100px !important` mobile override was tuned against the old `paddingTop: 140` desktop. The desktop padding is now 72 px, which makes the mobile being *larger* than desktop — unusual but not necessarily wrong (mobile nav is typically taller). Worth a deliberate decision rather than an accidental inversion.

**Fix:** Add an inline comment in `global.css` at line 584 documenting the *current* reason for the override, e.g.:
```css
/* Mobile: cancel the desktop 640px hero floor — phones use intrinsic content height
   so the URL bar / address bar doesn't push CTAs below the fold on first paint. */
header[class*="grain"] {
  min-height: auto !important;
  padding-top: 100px !important;
  padding-bottom: 64px !important;
}
```
And confirm with design that mobile `padding-top: 100px` > desktop `padding-top: 72px` is intentional (it likely is, due to the fixed nav, but the diff inverts the previous relationship).

### IN-04: `bringUpDevServer` polls for 30 s with no exponential backoff, but spawns shell-piped child without buffer drain

**File:** `server/tests/landing-page-golden.test.ts:23-38`
**Issue:** Pre-existing in this test (not introduced by 02.1; only the port literal moved). The `spawn(...)` uses `stdio: 'pipe'` but never reads the child's stdout/stderr. On a slow first build (cold Vite optimize-deps + Puppeteer launching), Vite can write enough log output to fill the OS pipe buffer (typically 64 KB on Linux, 16 KB on macOS), at which point the child blocks on a `write()` and the dev server stalls — making the 30-s ready-poll deterministically time out with a misleading "did not start within 30s" error. The phase doesn't make this worse, but the diff drew attention to it and it's a real CI-flake source. The threshold-lift means future failures are slightly less likely to come from pixels and slightly more likely to come from infrastructure (this), so worth recording.

**Fix:** Either drain the streams or discard them:
```ts
const child = spawn('pnpm', ['exec', 'vite', '--port', '5174', '--host', '127.0.0.1'], {
  stdio: ['ignore', 'ignore', 'ignore'],  // discard stdio entirely
});
```
Or attach `.on('data', () => {})` listeners to drain the pipes if logs are useful for debugging. Out of v1 scope; flag for the next test-infra cleanup.
