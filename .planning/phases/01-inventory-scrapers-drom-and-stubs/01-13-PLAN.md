1. `process.cwd()` is mocked at the suite level (`cwdSpy` set in `beforeAll`). The orchestrator writes paths via `resolve(<rel>)` which uses `cwd` — this is how the test sandboxes the FS. Re-use this; do NOT redo the mock per test.
2. The cursor file MUST be seeded at `<runRoot>/<runId>/.cursor.json` BEFORE invoking `drom.run({ resume: true })`. But the orchestrator generates a fresh `runId` from the system clock at start of `run()`, so the cursor file location must be known to the test in advance. **Mitigation:** the test seeds the cursor under a directory that matches the `runId` format and arranges for `inheritFromPrevCurrent` and the orchestrator's `mkdir runDir` to discover it. Concretely: the orchestrator creates `runDir = resolve(runRoot, runId)` then immediately calls `mkdir runDir, recursive: true`; if a cursor file with matching runId exists, `readCursor(runDir)` will find it.

   Because runId is generated dynamically and is hard to seed deterministically, the test uses a different strategy: instead of seeding the cursor under the new runId (which is unknown until `drom.run()` starts), it uses a **two-step run**: (a) start one `drom.run({ resume: false })` that crashes mid-run by throwing from a stubbed parser; (b) verify a cursor was written to the new runId; (c) inspect that runDir, modify the cursor file directly to a known state, then call `drom.run({ resume: true })` — which generates a NEW runId, but the orchestrator reads `.cursor.json` from the NEW `runDir`, which is empty.

   That two-step approach does NOT work because the orchestrator reads the cursor from the NEW runDir, not the old one. Looking at `drom/index.ts:216`: `cursor = await readCursor(runDir)` where `runDir = resolve(runRoot, runId)` and `runId = makeRunId()` is fresh per invocation.

   **The actual seeding approach (verified against `drom/index.ts`):** The orchestrator uses `runDir = resolve(RUN_ROOT_REL, runId)` and calls `mkdir(runDir, { recursive: true })` BEFORE `readCursor(runDir)`. Because `runId` is fresh on every invocation and the cursor file lives INSIDE `runDir`, there is no clean way to pre-seed it from outside.

   **Resolution:** mock the cursor module itself for the resume tests. Use `vi.doMock('../scrapers/shared/cursor.js', ...)` to return a controlled `readCursor` that yields the desired Cursor object on first call (or null, or throws `CorruptCursorError`). The `writeCursor` and `deleteCursor` mocks can be no-ops or pass-through. This is the same pattern the existing tests use to mock `parse-brand-index`, `parse-model-list`, etc.

   ```ts
   vi.doMock('../scrapers/shared/cursor.js', async () => {
     const actual = await vi.importActual<typeof import('../scrapers/shared/cursor.js')>(
       '../scrapers/shared/cursor.js',
     );
     return {
       ...actual,
       readCursor: async () => ({
         lastBrandSlug: 'bmw',
         lastModelSlug: 'x5',
         completedAt: '2026-04-28T12:00:00.000Z',
       }),
       writeCursor: async () => {}, // no-op so we don't actually write
     };
   });
   ```

   This gives full control over what the orchestrator sees as the cursor, without fighting the dynamic runId.
