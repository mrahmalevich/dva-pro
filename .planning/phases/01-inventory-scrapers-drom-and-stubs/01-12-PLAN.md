<objective>
Phase 1 gap-closure plan 12 — close the CR-04 data-loss bug by adopting the simpler-of-two remedies recommended in 01-REVIEW.md: document and enforce the contract "resume re-scrapes the cursored brand from scratch."

Why this is the right remedy (per the gap_summary in the orchestrator brief):
- The d3bad88 commit `inheritFromPrevCurrent` already preserves the previous successful run's records and images in the new run dir. After this plan, when a mid-brand crash occurs and the operator re-runs, `inheritFromPrevCurrent` brings the prior brand's records forward (so they are not lost from `models.json`), and the cursored brand is re-scraped from scratch (so its partial-aborted state is replaced atomically and brand-aliases for that brand are re-merged correctly).
- The alternative ("persist brandModels/records to disk after every model") is heavier I/O for diminishing returns now that the snapshot path exists.

This plan delivers two changes:
1. `server/scrapers/drom/index.ts` — when `cursor` is set AND `brand.brand_slug === cursor.lastBrandSlug`, set `startFromModelIndex = 0` regardless of `cursor.lastModelSlug`. Plan 10 left the inclusive-cursor logic in place for surface-level correctness; this plan stacks on top by additionally pinning the index to 0 for the cursored brand. The two changes compose: throw if cursor model is missing entirely (plan 10), but if it IS present, ignore it for positioning purposes (this plan's CR-04 contract).
2. `data/scraped/README.md` — rewrite §"Crash recovery (D-15)" so it honestly describes what the code does. Today (line 86–90) the README claims model-level resume the code does not actually deliver.

Out of scope:
- Sort-before-compare semantics (plan 10).
- Cursor file robustness (plan 11).
- Image bug-fixes (plan 14).
- Resume-path integration tests (plan 13).

Output: orchestrator with CR-04 contract enforced; README updated to match.

```markdown
### Crash recovery (D-15) — resume contract

If a `pnpm scrape:drom` run dies mid-brand, the next invocation reads `.cursor.json` and resumes with this contract:

1. **Prior brands are preserved verbatim** — `inheritFromPrevCurrent` copies records and images from the previous successful `current/` snapshot into the new run dir before scraping starts. Brands that completed before the crash do NOT need to be re-fetched.
2. **The cursored brand is re-scraped from scratch** — when the loop reaches the brand `cursor.lastBrandSlug`, `startFromModelIndex = 0`. Partial brand-aliases entries from the aborted brand are reconstructed because the brand is fully re-scraped and `mergeAliases` runs at end-of-brand on the complete set. Worst case: ~1 brand's worth of pages re-fetched (~7 hours at 10 s/req × ~30 pages/model × ~50 models for a brand-heavy entry like Toyota; smaller brands recover in minutes).
3. **Brands lexicographically after the cursored brand are scraped fresh** — they were never reached in the aborted run.
4. **A corrupt or hand-edited `.cursor.json` aborts the run loudly** — `readCursor` (post plan 01-11) distinguishes "file absent" (fresh start) from "file present but malformed" (`CorruptCursorError`, exit 1). Delete the file explicitly to start a fresh run after corruption.
5. **A `cursor.lastBrandSlug` no longer present in the catalog aborts the run** — `Cursor.lastBrandSlug='X' not present in current brand list` (plan 01-10). Either re-run without `--resume` semantics (delete `.cursor.json`) or correct the brand list (e.g. unset `DROM_BRAND_WHITELIST`).
6. **On clean completion `.cursor.json` is deleted.**

The brand-boundary granularity is a deliberate Phase 1 trade-off documented in `01-REVIEW.md` (CR-04). Finer-grained cursors (per-model checkpoint persistence) are a Phase 1.x candidate; the snapshot path makes the trade-off acceptable for v1 because no records are permanently lost — only the cursored brand's pages are re-fetched.
```
