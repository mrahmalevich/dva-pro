## Decisions Made

### H1 vs H3: hypothesis selection

**H1 (parser bug) — REJECTED** without spending live drom requests, on these grounds:

1. The committed fixture `server/tests/fixtures/drom/generation.bmw.x5.g05.html` contains exactly 9 engine-group `<tbody>` blocks, of which **only 2** contain a `<span class="_13wmddp1">Цена б/у:</span>` row. The other 7 engine groups have no «Цена б/у» row at all — so even a perfect parser cannot extract `price_used_from_rub` for trims under those 7 engine groups.
2. `extractTrimRows` in `parse-generation-page.ts:313-328` extracts `price_used_from_rub` at tbody scope (per engine group), then assigns the same value to every trim under that tbody. This is correct per drom's DOM — drom emits «Цена б/у» as an engine-group aggregate, not a per-trim value.
3. The selectors used (`_13wmddp1` containing `б/у` for used; `td.y7l57t0` containing `₽` for new) are consistent with the live HTML in the fixture.

H1 fixture spot-check budget (3 live fetches) was therefore not spent — drom is rate-limit sensitive and the structural evidence above is conclusive. This is permitted by the plan ("If H2/H3 alone is convincing without H1 evidence ... you may skip the live fetch and proceed straight to the threshold tune.").

### H2 — distribution check

`jq` against `data/scraped/drom/2026-05-03T05-05-16Z/models.json` (38 models, 477 complectations):

| Metric | Count | Ratio |
|---|---|---|
| `price_new_rub` present (per-trim) | 154 | 32.3% |
| `price_used_from_rub` present (per-engine-group) | 79 | 16.6% |
| BOTH new + used present | **40** | **8.4%** ← matches gate's 0.08 failure |
| Either new or used present | 193 | 40.5% |
| Neither present | 284 | 59.5% |
| `in_production` (year_to == null) → priced | 0 / 47 | 0.0% |
| Legacy (year_to != null) → priced | 154 / 430 | 35.8% |

The Pricing zod schema has 2 leaves and `THRESHOLDS.pricing = 2` (D-06: require BOTH non-null to count a trim as covered). The 0.70 floor is mathematically unreachable on drom — the joint-presence ceiling is ~17%, capped by drom's own per-engine-group «Цена б/у» sparsity.

The plan's a-priori narrative ("drom only carries pricing for in-production gens") is **inverted** by H2: in-production gens have 0/47 pricing on this run; legacy gens have 154/430. The actual story is per-engine-group sparsity, not generation lifecycle.

### H3 — threshold change

Introduced per-group `COVERAGE_FLOORS` map in `coverage.ts`:
```ts
const COVERAGE_FLOORS: Record<keyof FieldCoverage, number> = {
  identity: 0.70,    // unchanged
  pricing: 0.05,     // ← new floor (drom-aware)
  drivetrain: 0.70,  // unchanged
  dimensions: 0.70,  // unchanged
  comfort: 0.70,     // unchanged
  tires: 0.70,       // unchanged
};
```

`meetsCoverageGate` rewritten to consult this map per group instead of comparing every value to a single `0.70` literal. Behavior preserved for the 5 unchanged groups (verified: 9/9 existing coverage tests still pass).

**Expected new pricing coverage on the 2026-05-03 run:** 0.08 (unchanged — same data, same parser; the change is purely the gate's tolerance). Gate now PASSES because `0.08 >= 0.05`.

**Why 0.05 specifically:**
- 0.00 would not detect a full-pricing regression
- 0.08 (the structural ceiling) would fail on any natural variation downward
- 0.05 sits below the 0.08 ceiling with margin for natural per-run variance, but high enough that a fully-broken pricing extractor (0.00) trips the gate
